# CCL Integration

## Causal Context Ledger for Open Calculator

**Status:** canonical documentation architecture, implementation scaffold in progress  
**Public name:** CCL v1 — Causal Context Ledger

---

## 1. Purpose

Open Calculator contains product rules, distributed-systems hypotheses, economic parameters, model-generated interpretations, benchmark results, failed experiments, and implementation evidence. A normal README is not sufficient to preserve the status and causal history of all these claims.

CCL is the public evidence and decision-memory layer for the project. It exists to answer:

- What is currently believed to be true?
- Which facts are verified by implementation or test evidence?
- Which designs are experimental?
- Which ideas were replaced or rejected?
- Which claims remain unverified?
- Which evidence is unsafe, incomplete, or inconsistent and therefore quarantined?
- What exact decision or experiment should happen next?

CCL does not replace source code, tests, or peer review. It provides a deterministic map between them.

---

## 2. Core principles

### 2.1 Fact first

The ledger records observed or explicitly decided values. Missing information is represented as `unknown` or `null`; it is not inferred merely to make a document look complete.

### 2.2 Current truth is separate from history

`state.json` represents the current public state. Append-only history records how that state changed. Rewriting current state does not erase the prior decision path.

### 2.3 Minimal deterministic updates

A task changes only the surfaces required by its contract. Generated files must be regenerated by a stable procedure rather than edited inconsistently by hand.

### 2.4 No silent repair

A broken reference, missing evidence object, schema mismatch, or inconsistent hash is an explicit failure. The system does not invent a replacement or drop the edge quietly.

### 2.5 Referential integrity

Every evidence identifier, decision identifier, experiment identifier, and source reference resolves or is explicitly marked unresolved.

### 2.6 Failure is evidence

A failed benchmark, rejected protocol, or implementation blocker remains useful. It must not disappear merely because a later attempt succeeds.

### 2.7 Public boundary

The public CCL contains only information safe for a public repository. Credentials, private keys, private hosts, personal contact data, local machine paths, session identifiers, and private infrastructure topology are not ledger evidence.

## 3. Status vocabulary

Every substantial record uses one of the following statuses.

### `canonical`

Accepted current design, verified implementation truth, or current project decision.

Examples:

- one authoritative result order is required;
- stale Equal attempts must not be charged;
- GPT-5.6 does not control balances;
- public safety is fail-closed.

### `experimental`

A falsifiable candidate that has a defined evaluation or promotion gate.

Examples:

- a 40 ms active micro-epoch target;
- SAI EpochCast dual-lane delivery;
- Rust/WebAssembly incremental evaluator;
- a particular cult settlement cadence.

### `superseded`

A prior design replaced by a newer decision. The record remains for causal history.

### `rejected`

A design deliberately not pursued, with a reason.

Examples:

- giving GPT authority over rarity or ownership;
- direct sequencer fan-out to every spectator as the intended high-scale architecture;
- using JavaScript `eval` for expressions.

### `unverified`

A plausible claim lacking adequate evidence.

Examples:

- a target audience size;
- expected CDN request collapse;
- a claimed cost reduction;
- novelty relative to all prior systems.

### `quarantined`

A record withheld from normal decision or publication flow because it is unsafe, incomplete, contradictory, stale, or lacks required provenance.

## 4. Repository layout

```text
ccl/
├── state.json
├── ref_index.ndjson
├── history/
│   └── README.md
├── compact/
│   └── README.md
├── quarantine/
│   └── README.md
└── schema/
    └── state.schema.json
```

### `state.json`

The current public snapshot of project truth and research status.

### `ref_index.ndjson`

One reference object per line. It maps stable reference identifiers to public files, commits, tests, benchmark artifacts, or external primary sources.

### `history/`

Append-only state-transition and decision records.

### `compact/`

Generated compact views for tools or constrained contexts. Compact views never become independent truth.

### `quarantine/`

Unsafe or insufficient evidence is not committed here in raw form. Public quarantine records contain only sanitized metadata explaining why a claim was excluded.

### `schema/`

Machine-readable schemas for public CCL objects.

## 5. State model

A public state object may contain:

```json
{
  "schema_version": "ccl.opencalculator.state.v1",
  "project": "Open Calculator",
  "updated_at": null,
  "classification": "experimental_public_design",
  "canonical": {},
  "experimental": {},
  "unverified": {},
  "rejected": {},
  "known_limitations": [],
  "evidence_refs": [],
  "next_task": null
}
```

`updated_at` remains `null` until a deterministic update procedure owns it. A documentation author must not fabricate timestamps or benchmark metadata.

## 7. Record shape

A decision or experiment record should include:

```text
record_id
record_type
title
status
statement
reason
preconditions
supersedes[]
superseded_by?
evidence_refs[]
limitations[]
promotion_gate?
created_by_class
created_at?
```

`created_by_class` may be one of:

```text
human_direction
SAI_design_agent
Codex_engineering_agent
deterministic_generator
benchmark_harness
reviewer
```

This records provenance class without exposing personal data or private session metadata.

## 9. Evidence rules

### 9.1 Primary evidence

Preferred evidence includes:

- committed source code;
- deterministic test output;
- benchmark artifacts with environment metadata;
- public pull-request diff;
- schema validation output;
- fault-injection report;
- official platform documentation;
- independent replay witness output.

### 9.2 Insufficient evidence

The following alone do not promote a claim:

- an architecture diagram;
- an AI-generated explanation;
- a target number;
- one anecdotal successful run;
- a screenshot without reproducible context;
- a Merkle root without the canonical manifest and execution witness;
- a passing result against a stale commit.

### 9.3 Exact-head rule

Implementation evidence must identify the exact public commit or pull-request head it verifies. A result from an earlier head cannot silently certify a later change.

### 9.4 Baseline classification

A pre-existing failure is not treated as a new regression, but the classification needs evidence:

- the failure exists on the baseline;
- the changed scope does not affect it;
- focused tests for the new work pass;
- the final report preserves the unresolved failure.

## 10. Quarantine

Quarantine is metadata-first. Dangerous raw content is not copied into the repository simply to prove that it was dangerous.

A sanitized quarantine record may state:

```text
finding_id: SAFE-2026-001
rule_id: PRIVATE_KEY_BLOCK
path_class: generated_artifact
raw_value_stored: false
status: blocked
resolution: artifact excluded and generator corrected
```

The public record never includes the matched credential, private hostname, personal email address, local path, or token.

---

## 11. Generated surfaces

Generated views may include:

- current-state Markdown;
- compact JSON;
- protocol promotion matrix;
- benchmark summary;
- decision timeline;
- evidence graph;
- next-task handoff.

Generated content must declare its source and generator version. Manual edits to managed blocks are rejected or overwritten by deterministic generation.

---

## 12. Update contract

A CCL update should follow this sequence:

1. read current state and relevant history;
2. validate schema and references;
3. identify the smallest required status transition;
4. write the new evidence record;
5. update current state;
6. regenerate compact views;
7. run reference and public-safety checks;
8. verify exact-head consistency;
9. publish through review.

Any failed step leaves the update incomplete. The system must not claim a successful transition because only one surface was changed.

## 13. CCL and SAI EpochCast

EpochCast is a strong example of why CCL is necessary. Its architecture is intentionally ambitious and can sound conclusive before evidence exists.

CCL keeps separate:

- the canonical need for one authoritative order;
- the experimental 40 ms epoch target;
- the unverified expectation of spectator request collapse;
- the rejected direct-per-spectator authority design;
- any benchmark result that passes promotion gates;
- any failure that forces a protocol revision.

The protocol can therefore be presented boldly without confusing invention with validation.

---

## 14. CCL and model-assisted development

Model assistance increases design velocity but also increases the risk of coherent-sounding unsupported claims. CCL provides a counterweight.

A model may:

- propose a protocol;
- identify an invariant;
- generate a test;
- summarize evidence;
- propose a status transition.

A model may not, by prose alone:

- turn an experiment into a fact;
- invent a benchmark result;
- hide a failing test;
- repair a broken reference silently;
- publish unsafe private data;
- promote its own generated implementation without evidence.

## 16. Conclusion

CCL makes Open Calculator’s technical ambition safer to publish. It preserves an explicit distinction between what the project wants, what it has designed, what it has implemented, what it has measured, what has failed, and what must not be exposed publicly.

The ledger’s value is not that it makes every decision permanent. Its value is that every change remains explainable.
